## Copilot สำหรับงานวิทยาศาสตร์ข้อมูล

ผู้ช่วยใน Notebook ที่เข้าใจบริบท workspace, lakehouse และโครงสร้างโน้ตบุ๊ก:

- สร้าง ปรับโครงสร้าง และสรุปโค้ด
- ช่วยวินิจฉัยข้อผิดพลาด
- เร่งงานซ้ำ — **ผู้เรียนยังต้องตรวจสอบตรรกะและหลักฐานเอง**

ใช้เพื่อเร่งงาน ไม่ใช่แทนที่การสำรวจข้อมูล สัญญาข้อมูล และตัวชี้วัดธุรกิจ

## Semantic Link

สะพานระหว่าง **Power BI Semantic Model** (นิยามตาราง ตัวชี้วัด และความสัมพันธ์ทางธุรกิจ) กับโค้ด Python ในงานวิทยาศาสตร์ข้อมูล:

- ดึงตารางหรือตัวชี้วัดที่ผ่านการรับรองมาเป็นฟีเจอร์ หรือใช้ตรวจความสอดคล้องของตัวเลข
- ลดปัญหา “ทีมรายงานนิยาม churn คนละอย่างกับทีมโมเดล”

แนวทางองค์กรที่แนะนำจากสไลด์:

1. Semantic Model เป็นสัญญาธุรกิจ (นิยามตัวชี้วัดกลาง)  
2. วิศวกรข้อมูลจัดชั้น Bronze/Silver ให้ตรงสัญญา  
3. นักวิทยาศาสตร์ข้อมูลฝึกโมเดลและเขียนผลทำนาย  
4. นักวิเคราะห์ใช้ตาราง Gold พร้อมตัวชี้วัดเดิม ผ่านโหมดอ่านตรงจาก OneLake  

## Responsible AI — หลักความรับผิดชอบ

โมเดลแม่นแต่ไร้ธรรมาภิบาล = ความเสี่ยงองค์กร

แนวปฏิบัติที่ต้องคุยในทีม:

- ความเป็นธรรม และการตรวจสอบอคติในผลทำนาย  
- ความน่าเชื่อถือและความปลอดภัย  
- ความโปร่งใส / อธิบายได้พอใช้ตัดสินใจ  
- ความเป็นส่วนตัวของข้อมูลลูกค้า  
- ความรับผิดชอบ (ใครอนุมัติโมเดลขึ้นระบบจริง)  
- ผลกระทบต่อผู้ใช้ปลายทาง  

สำหรับ churn: ระวังการใช้ฟีเจอร์ที่อ่อนไหว และการส่งแคมเปญที่เลือกปฏิบัติโดยไม่ตั้งใจ

## บริหาร Capacity และต้นทุน

- หน่วยความจุ (Capacity Units) มีจำกัด — การเปิด Spark session, ขนาดข้อมูล และการฝึกโมเดลซ้ำมีต้นทุนจริง  
- ปิด session ที่ไม่ใช้, ใช้ชุดตัวอย่างตอนสำรวจ, เลือกทำนายเป็นชุดแทนแบบทันทีเมื่อธุรกิจยอมรับได้  
- วางตารางชั้นคุณภาพให้ไม่ต้องอ่านข้อมูลดิบทั้งก้อนทุกครั้งที่ฝึกโมเดล

## สรุปโมดูล

| เครื่องมือ | คุณค่า | ข้อจำกัด |
| --- | --- | --- |
| Copilot | เร่งโค้ดและแก้บั๊ก | ต้องตรวจสอบผล |
| Semantic Link | ตัวชี้วัดตรงกับรายงาน | ต้องมีโมเดลความหมายที่ดูแลดี |
| Responsible AI | ลดความเสี่ยงหลังขึ้นระบบ | ต้องมีกระบวนการ ไม่ใช่สไลด์เดียว |
| ดูแล Capacity | คุ้มค่าการเรียนและการผลิต | วัดและทบทวนเป็นรอบ |
